## ROOT-CAUSE DIAGNOSTIC — the failures are provider-side quota/capacity, not our code

Ran the full offline-first diagnostic the brief asked for. **8 new live requests**
(3 differential matrix + 3 replication + 2 provenance). No product code changed.

### Decisive evidence

| Probe | Payload | Result |
|---|---|---|
| A_MINIMAL | 126 B, tiny prompt, no `response_format` | **200 OK** (14.0 s) |
| B_STRUCTURED_MINIMAL | A + `response_format: json_object` | 503 (3.7 s) |
| C_FULL_RIDER | production Rider payload, 17 396 B | 503 (1.6 s) |
| A2 (repeat of A, byte-identical) | | **503** |
| B2 / B3 (`json_object` / `json_schema`) | | 503 / 503 |
| P1 via proxy / P2 direct, identical payload | | **429 / 429** |

**A false positive, corrected.** A→200 while B→503 looked like `response_format` was
the cause. Replication killed it: A2, byte-identical to A, returned 503. The outcome
varies **across identical requests** → intermittent, server-side. `response_format`
is exonerated; do not "fix" it.

**The 429 is the answer.** P1/P2 returned HTTP 429 with a body beginning
`"code": 429, "message": "You exceede…` — quota exhausted — and **identical results
through the proxy and direct**, so our egress path is not involved.

The repo already knew: `docs/stage4c-advocate-benchmark.md` says
`GEMINI CHARACTERIZATION : PENDING — QUOTA EXHAUSTED` and records a prior 429 with no
`Retry-After`.

### Ruled out, with evidence

- **Config** — base URL, model, key hygiene, precedence, single 8000 listener: all correct.
- **Endpoint form** — `.../v1beta/openai/chat/completions`, no double `/v1`, no missing `/openai`.
- **Request shape** — 2 messages (system/user), `temperature 0`, `max_tokens 8192`,
  no `reasoning_effort`, no `stream`, 17.4 KB body, ~4.3k est. input tokens. Small and valid.
- **Payload size / schema** — the JSON schema is **never sent**; `complete()` ignores
  `request.response_schema` and hardcodes `{"type": "json_object"}`. Schema complexity
  cannot reach the wire. The schema appears once, inside the system prompt.
- **Prompt duplication** — none. 9305 = 2784 + 1941 + 4108 + wrapper, each exactly once.
  No stale Ollama/Qwen references.
- **Connection pooling** — a **fresh `httpx.Client` per attempt** (inside the retry loop),
  so no stale-pool or keep-alive reuse is possible.
- **Local proxy** — `HTTP(S)_PROXY=http://127.0.0.1:60811` is set and httpx defaults to
  `trust_env=True`, so requests do traverse it. But the proxy forwards correctly
  (`www.google.com/generate_204` → 204 in ~300 ms) and direct-vs-proxied give identical
  results. Not the cause.

### Anomaly worth a decision

Every response carries `Server: scaffolding on HTTPServer2` — not a Google banner — even
though DNS resolves the host to real Google IPs (172.217.115.4). Whatever answers is a
scaffolding/stub layer. Recorded as an observation; it does not change the conclusion
that the failures are emitted by the endpoint rather than by our request.

### Product findings (none of them cause this outage)

1. `408` maps to `REQUEST_REJECTED` (non-retryable) — arguably should retry. Minor.
2. The 503 backoff is `1.0 * 2^(n-1)` = **1 s** — very aggressive against a saturated
   endpoint; the code's own comment argues for waiting.
3. On failure the provider records only a status code. Adding an opt-in, dev-only
   capture of the `Server` banner and Google's canonical `error.status` enum would have
   made this diagnosis a one-call job. The "never surface the body" property should stay.
4. `_safe_error_category` in the diagnostic tooling expected a dict body; this endpoint
   returns `[{...}]` (an array), so the category came back null. Tooling-only.

**Verdict: no production code change is needed to fix this. Another live Stage 6 run is
NOT justified until quota is restored.**
