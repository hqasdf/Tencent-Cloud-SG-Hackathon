# 2026-09-29 — RydeResolve

## Frontend case page rebuilt as a numbered step workflow

### Why

The user's report: *"the front end ui is very complicated n hard to understand n use"*.
Clarified via AskUserQuestion to: primary user = **ops agent triaging**, structure =
**step by step to show the workflow n steps, must be user friendly**.

Diagnosis of the old `CaseDetail.tsx`: one `<main>` stacking ~16 sections. The answer
(outcome, refund, confidence) sat at the bottom, after the timeline, the evidence table
and an audit log. The same numbers appeared in up to three places (Judge panel,
deterministic panel, lower `decision-grid`). Internal labels leaked into user-facing copy
("Stage 6 · Full pipeline", "the Stage 5 panel above"). Two competing run buttons existed
("Run advocates" and "Run resolution"). Claim ids were shown everywhere with no
plain-language summary.

### What changed (all frontend, no backend change)

New `frontend/src/components/WorkflowStep.tsx`:
- `WorkflowStep` — numbered collapsible step card: number badge, title, one-line summary,
  text status pill (`Done` / `Next` / `Not run` / `Blocked` / override), chevron, and a
  Back / "Step N of M" / Next footer inside the open body.
- `WorkflowRail` — wrapping chip rail above the steps, each chip clickable, showing the
  same state. **Wraps rather than scrolls**: a step hidden behind a horizontal scrollbar
  is a step the operator will not notice exists.
- `StepPending` — dashed placeholder for a step that cannot run yet. A waiting step is not
  a broken step, so it is not greyed out.

`CaseDetail.tsx` rewritten around **eight steps**: Review the case → Examine the evidence →
Check the facts → Read the arguments → Cross-examination → The Judge's view → The decision
→ Why this decision.

Three rules the file now encodes:
1. **One primary action.** "Run full analysis" appears exactly once, in the toolbar. The
   cheaper two-call path is a subordinate ghost button ("Advocates only") beside it, and it
   disappears once a full run exists.
2. **Every number has one home.** The deterministic outcome is stated in step 7 and nowhere
   else; confidence is stated in step 3 and nowhere else. The fixture's pre-computed
   `resolution`, `confidence` and `activity` fields are deliberately **not rendered** — the
   live pipeline supersedes them and showing both is what created the duplicates.
3. **No internal stage names.** Steps are named after what the operator is looking at.

Component splits made to support this:
- `JudgePanel.tsx` — `JudgePanel` (the two-column composite) removed; now exports
  `JudgeAdvisoryPanel`, `DeterministicOutcomePanel`, `AuditTrail`. The advisory/deterministic
  separation is now enforced by *sequence* rather than by two adjacent columns: step 6 is
  framed "recommendation only … stated in the next step", step 7 is the only place an outcome
  appears. The weight difference is preserved — nothing from the Judge renders as a decision.
- `AdvocateRun.tsx` — `AdvocateRunPanel` (which carried its own run button, provider badge
  and "Stage 4" eyebrow) removed; now exports `AdvocateArguments` (rider, driver, pipeline,
  verificationSummary) with no action and no provenance badge.

Also: `humanize()` added to `utils/format.ts`. `labelize` alone turns `CONTRADICTORY_EVIDENCE`
into "CONTRADICTORY EVIDENCE"; `humanize` lowercases first, giving "Contradictory Evidence".
Applied to escalation reasons, rejection reasons and resolution modes.

Step 7's "Human reviewer brief" block was **removed**: `caseData.humanReviewSummary` is the
server's `"Deterministic escalation reasons: A, B, C"` string, i.e. the same list the outcome
panel above already renders — and renders in readable words. Replaced with an "Action required"
callout that states the *consequence* instead ("the deterministic engine will not act on this
case by itself"), which is the part that was actually missing.

### Environment gotchas found

- **A zombie Vite process held port 5173.** `TaskStop` reported the task killed but the node
  child survived, so a restarted dev server silently moved to 5174 and every request to 5173
  was served stale code — which looked exactly like a broken file watcher. Kill by port with
  `Get-NetTCPConnection -LocalPort 5173 -State Listen` then `Stop-Process -Id <pid> -Force`.
  Diagnose staleness by curling the module: `curl http://127.0.0.1:5173/src/components/X.tsx`.
- `agent-browser screenshot <path>` treats the first positional arg as a **selector**, not a
  path. Use `--screenshot-dir <dir>`.
