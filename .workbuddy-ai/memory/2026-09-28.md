### Production defect found and fixed

## Stage 5 — Judge Agent (implemented, validated offline, no live Judge call)

### Architecture

Pipeline: `deterministic analysis → Rider → Driver → claim verification →
JudgeContextBuilder → JudgeAgent → JudgeOutputValidationService → deterministic remedy`.

`AdvocateOrchestratorService` is **reused unchanged** (its response type is
`AdvocateRunResponse` and §19 requires `/advocates/run` to stay compatible), so a new
`ResolutionOrchestratorService` sequences the whole thing into `CaseResolutionResponse`.
`AdvocateOrchestratorService.run` gained an **optional** `context=` parameter so Stage 5
builds one projection and shares it with both the advocates and the Judge.

### Design decisions worth keeping

- **Outcome vocabulary is the repo's, not the brief's.** `ResolutionEngine` emits
  `NO_REFUND`, `PARTIAL_REFUND`, `FULL_FARE_DIFFERENCE_REFUND`,
  `UPHOLD_CANCELLATION_CHARGE`, `REFUND_CANCELLATION_CHARGE` (+ `HUMAN_REVIEW`, which is
  deterministic-only). The brief said `FULL_REFUND`; the repo does not have it.
- **Claim IDs must be namespaced** (`RIDER-C1` / `DRIVER-C1`). Both advocates start at
  `C1`, so a bare `C1` is ambiguous across sides and §9's "validate all references" is
  unenforceable without it. `app/agents/judge_claims.py` owns this.
- **Rejected claims are excluded entirely, not labelled.** A prompt section saying "not
  trusted" still puts the assertion in the context window. Exclusion is structural.
- **`extra="forbid"` on `JudgeOutput`** is what makes "the Judge cannot state an amount"
  a guarantee rather than a request — a smuggled `refundAmount` is a schema failure.
- **The Judge's `status` is computed by code**, not copied from the model. A model
  claiming `COMPLETE` when the gate says HUMAN_REVIEW gets `HUMAN_REVIEW_OVERRIDE_ATTEMPTED`
  and the whole response is rejected.
- Money in prose is checked against the trusted numeric facts: quoting a supplied value is
  fine, inventing one is `INVENTED_MONETARY_VALUE`.

### Bugs found and fixed during implementation

1. `ResolutionOrchestratorService` did not pass its injected `provider` down to the
   advocate orchestrator, so a stub only affected the Judge and the advocate path silently
   resolved its own provider. Fixed.
2. Namespacing ran *before* the wrong-side check, turning a foreign `DRIVER-D1` into
   `RIDER-DRIVER-D1` and reporting `UNKNOWN_CLAIM_ID` instead of
   `CLAIM_ID_BELONGS_TO_OTHER_SIDE`. Fixed by splitting the side prefix first.

## Stage 6 — Bounded Rebuttal / Cross-Examination + Explainability (implemented, validated offline, no live call)

One bounded rebuttal round between claim verification and the Judge. **Hard constraint: no new
autonomous agents, no unbounded agent conversations.** Both honoured.

### Architecture

`Initial Rider → Initial Driver → claim verification → Rider rebuttal → Driver rebuttal →
rebuttal verification → Judge`. Rebuttal is a *response* layer, not a second evidence-gathering
phase: it may only reference evidence/policy already in the trusted context.

### Structural (not runtime) guarantees — the load-bearing idea

- **One round is unrepresentable, not disabled.** `RebuttalCaseContext` has no field that could
  name a rebuttal as a target, so `Rider rebuttal → Driver rebuttal-to-rebuttal` cannot be
  expressed. `MAX_REBUTTAL_ROUNDS = 1` is a constant, not a config knob.
- **Rejected material is never read, not filtered.** `JudgeContextBuilder._rebuttals()` reads
  `verified_rebuttals` only; there is no `rejected_rebuttals` parameter to forget to filter.
  Same pattern as Stage 5's `_side()`. Absence from the type is the guarantee.
- **`extra="forbid"`** on `RebuttalModel` — an invented field is a schema failure, not a
  silently dropped extra.
- **Code assigns rebuttal IDs** (`RIDER-RB1`, dense, over verified responses only). Deliberate
  asymmetry with claim IDs, which the advocate authors and code merely prefixes.

### Failure policy is deliberately asymmetric

- **Initial advocate failure → Judge NOT_RUN** (`ADVOCATE_INPUT_INCOMPLETE`). Unchanged from
  Stage 5. No rebuttal attempted. The arguments *are* the case.
- **Rebuttal failure → does NOT block the Judge.** Rebuttals are supplementary. Failure is
  recorded, not fabricated around; a missing rebuttal is never replaced with invented content.
- **Zero verified rebuttals is a valid, non-degraded state.** Judge still runs.
- `PROVIDER_FAILURE` / `MODEL_OUTPUT_FAILURE` / `INTERNAL_ERROR` kept distinct — a 503 is never
  a hallucination.

### Real defects found and fixed

1. **`JudgeSideClaims` had no camelCase aliases.** Serialized Judge prompt mixed `verifiedClaims`
   with `verified_claim_count` while every sibling used camelCase — a mixed-convention payload
   invites the model to echo the wrong convention back. Fixed in `models/judge.py` (product fix,
   not a test fix).
2. **Stage 5 test broke legitimately.** `test_audit_trail_records_the_full_success_sequence`
   asserted the exact audit list; Stage 6 prepends rebuttal events. Now asserts the Judge's events
   as an **ordered subsequence** + rebuttal-precedes-Judge. Asserting the whole list would make
   every future stage break a Stage 5 test for no reason.
3. Two test bugs of my own: a hardcoded `DRIVER_PICKUP_DISTANCE_METERS: 60.0` against a real
   trusted `0.0` (now read from `deterministic_facts`), and a `CaseService()` call missing its
   `repository` argument.

### Deterministic explainability / counterfactuals

`DecisionExplanationService.build()` and `CounterfactualService.build()` project from trusted
structures only — no new factual claims. Counterfactuals vary **only** deterministic inputs tied to
explicit PolicyTwin thresholds (`waiting duration: 480 → threshold 300`), never hypothetical
evidence. `generated_by: Literal["DETERMINISTIC_ENGINE"]` makes the provenance explicit.
Direction derivation matters: `ROUTE_UNEXPLAINED_DEVIATION` and `NO_SHOW_WAIT_TIME` pass when
actual ≥ required (so fail `BELOW`), `NO_SHOW_PICKUP_RADIUS` passes when actual ≤ required (so fail
`ABOVE`). Backwards yields fluent, confident, wrong output.
